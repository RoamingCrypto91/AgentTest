Reverie

Every program here runs backwards. Not replayed from a log — there is no log. Each instruction has an exact inverse, and running a program in reverse is those inverses in the opposite order.

A conventional processor erases constantly: every x = y throws away whatever x held. Landauer’s principle says that costs energy — kT ln 2 per bit, and it is the only floor computation has. Bennett showed the floor is avoidable.

Reverie is what that looks like as a language you can actually run. It has no assignment. Its conditionals carry two predicates. Its debugger travels backwards through a program without recording anything, because the machine can simply run the other way.

idea 01A conditional carries two predicates

The test at the top chooses the branch on the way in. The predicate after fi must be true when the then-branch finishes and false when the else-branch does.

That is exactly what a reader of the reverse execution needs in order to know which way control went — so the machine needs no branch history at all. Here swapped is the witness: one, if the swap happened. Loops carry the same pair — from is an entry assertion, until the exit test.

idea 02An update may not read what it writes

x += f(y) is undone by x -= f(y), which is only correct if f(y) evaluates identically before and after. So the compiler refuses the alternative, and says why.

Four rules like this one — checked statically, before anything runs — are enough to guarantee a whole program is injective.

idea 03Inversion is an operation, not a feature

A sequence inverts by reversing it. A conditional swaps its two predicates. A loop swaps its entry assertion with its exit test. call and uncall swap; so do local and delocal.

Even print has an inverse. Output is information, so an inverted program does not print again — it un-prints, consuming the log the forward program produced.

The same transformation is available inside the language as undo { … }, and the compiler implements it by calling .invert() on the IR it has just built.

idea 04Destructive code, without the erasure

Inside an embed block you write what you would write anywhere: = assigns, while loops, temporaries get overwritten. The compiler pays for it with a history tape — and then hands the tape back.

Compute, copy the answer out, uncompute. Everything the classical code scribbled is put back exactly where it was found. Drag plate 1 to square root and watch the tape climb, hold, and drain.

idea 05An inverse nobody wrote

fib maps an index to a Fibonacci pair, consuming the index to zero as it goes. Nothing in it is special-cased for inversion.

But every statement in it has an inverse, so uncall fib is a program that takes a Fibonacci pair and tells you its index. That program does not appear in the source. The compiler derived it.

how it is testedReversibility is its own oracle

A reversible language admits a specification that needs no expected outputs: forward then backward is the identity on machine state — every cell, every stack, every line of output, every entry of the tape.

So the test suite generates programs nobody wrote — valid by construction — and checks that identity, that rev invert really produces the inverse, that the two independent inverters agree, and that the debugger’s goto lands exactly where stepping would.

The property that mattered was per-step, not end-to-end: from every reachable point, step back and forward again and demand bit-for-bit equality of state and program counter. Round-tripping a whole program only shows the composition is the identity. Errors that cancel survive it. Three did.

off by one

Conditionals took one extra instruction backwards. Harmless at the ends of a run; fatal if you reverse in the middle of a branch.

split pair

A classical while counted iterations in one instruction and uncounted them in another, so the loop balanced overall while individual transitions were not inverses.

buried bit

The classical branch bit was written before the branch ran, so at the join it sat underneath everything the branch had recorded. Reversing popped a value the body owned and used it to choose a branch. It cancelled often enough to pass some six hundred round-trip tests.

All three are the same failure of imagination: treating “the whole thing reverses” as if it meant “each step reverses”. In a machine that supports stopping and turning around, it does not.

That property is now a switch. rev run --paranoid takes each step, undoes it, checks that nothing moved, and redoes it — so any program, not only a generated one, can be held to it.

and thenThe same oracle, pointed at your code

Everything above tests the implementation. The same property tests programs. A procedure here already carries its specification — every fi predicate, every loop’s entry assertion, every delocal expression is a claim the machine checks — so nobody has to write an expected answer down.

rev verify builds a driver around each procedure, hands it random arguments, and checks two things: that forward-then-backward restores the starting state, and that call f followed by uncall f leaves it alone. The second is not the first run twice — it enters the body at the far end, with time still pointing forwards.

A random counterexample is unreadable, so it gets shrunk: try simpler inputs, keep whichever still fails, stop when nothing simpler does.

Not every procedure is total. swap_at(xs, i, j) is not reversible for i = -1, and reporting that as a bug is reporting a missing sentence of documentation. So a procedure states its domain in its doc comment, in ordinary Reverie — a condition to filter inputs, a pinned value for a needle no filter would find, or the name of code that builds a state no predicate can describe.

Writing those annotations for the shipped library was itself the test. It turned up six undocumented preconditions and one real interpreter bug: x >> -1 raised a Python error instead of trapping.

prior art

The surface language owes its shape to Janus (Lutz & Derby, 1986). embed is Bennett’s compute–copy–uncompute (1973, 1989). The thermodynamic framing is Landauer’s (1961).

New here: a bytecode machine whose program counter is a boundary index, so reversing time costs two sign flips; frames that survive being entered forwards and left backwards; and a test methodology that turns the language’s defining property into the oracle.
